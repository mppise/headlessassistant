Overview

The agent-server has a layered configuration model. The separation is intentional — infrastructure (SAP AI Core credentials, port) lives in environment variables; domain logic (which tools exist and what they do) lives in plain JSON and JavaScript files that require no server restart to add.

_DEMO/agent-server/
├── .env ← SAP AI Core credentials + server settings
├── lib/system-prompt.txt ← LLM persona, tone, boundaries, and tool guidance
├── tools/tool-registry.json ← declares which tools exist
└── tools/
    ├── get_customer_summary/
    │   ├── schema.json ← LLM tool definition (JSON Schema)
    │   └── handler.js ← execute(args, context) implementation
    ├── get_open_items/ …
    └── …
Adding a new tool requires zero changes to any server file. Create a schema.json and a handler.js, add one entry to tool-registry.json, and restart the server.

Environment variables (.env)

Create _DEMO/agent-server/.env by copying the template below. All variables are required unless marked optional.

# SAP AI Core — LLM inference AICORE_AUTH_URL=https://<your-subaccount>.authentication.<region>.hana.ondemand.com AICORE_BASE_URL=https://api.ai.prod.<region>.aws.ml.hana.ondemand.com AICORE_CLIENT_ID=sb-<client-id>!b<num>|aicore!b<num> AICORE_CLIENT_SECRET=<client-secret> AICORE_LLM_DEPLOYMENT_ID=<deployment-id> AICORE_LLM_MODEL=gpt-4o # optional — defaults to gpt-4o AICORE_RESOURCE_GROUP=default # optional — defaults to "default" AICORE_API_VERSION=2024-02-01 # optional — defaults to 2024-02-01 # Server PORT=3000 # optional — defaults to 3000
VariableRequiredDescription
AICORE_AUTH_URL✅ OAuth2 token endpoint base URL for your SAP BTP subaccount. Format: https://<subdomain>.authentication.<region>.hana.ondemand.com. The server appends /oauth/token.
AICORE_BASE_URL✅ SAP AI Core inference API base URL. Format: https://api.ai.prod.<region>.aws.ml.hana.ondemand.com.
AICORE_CLIENT_ID✅ OAuth2 client ID from your AI Core service binding.
AICORE_CLIENT_SECRET✅ OAuth2 client secret from your AI Core service binding.
AICORE_LLM_DEPLOYMENT_ID✅ The deployment ID of the LLM model you want to use. Find this in the AI Core resource group under "Deployments".
AICORE_LLM_MODEL Model name passed in the request body. Default: gpt-4o. Must match what the deployment ID targets.
AICORE_RESOURCE_GROUP AI Core resource group. Default: default. Sent as the AI-Resource-Group request header.
AICORE_API_VERSION AI Core API version query parameter. Default: 2024-02-01.
PORT HTTP port the server listens on. Default: 3000. See Server port.
Security: Never commit .env to version control. The file contains OAuth2 credentials — treat it like a password. The .gitignore excludes it by default.

Variables no longer used

These variables were present in earlier releases and can be removed from your .env:

  • EPP_COMP_CODE — removed in v2026.05.16.2031. Account context is now caller-supplied via the request body.
  • EPP_CUST_NUM — same as above.

System prompt

The LLM's persona, tone, scope boundaries, and tool guidance are defined in lib/system-prompt.txt. This is the primary lever for customising the assistant's behaviour without writing code.

The file is loaded once at startup and prepended to every conversation as the system message. Edit it to:

  • Change the assistant's name, persona, or tone.
  • Define what the assistant can and cannot do.
  • Describe each tool so the LLM knows when to call it (see the ## Tools available section in the default prompt).
  • Set response format expectations (e.g. "use markdown", "keep responses under 4 paragraphs").
You are a billing collections agent for Cardinal Rx, an online specialty pharmacy. Your role is to help patients understand and resolve their outstanding balances… ## Tools available - **get_customer_summary** — Best first call for general "what do I owe?" questions. - **get_open_items** — Detailed list of open invoices and/or credit memos. …
Always include a ## Tools available section that describes each registered tool, its purpose, and when to use it. The LLM uses these descriptions to decide which tool to call — a good description reduces unnecessary tool calls and improves answer quality.

Tool registry (tool-registry.json)

tools/tool-registry.json is the single configuration file that declares every tool the agent can use. Each entry maps a tool name to its schema and handler files.

[ { "name": "get_customer_summary", "statusMessage": "Pulling together your account summary…", "schema": "./tools/get_customer_summary/schema.json", "handler": "./tools/get_customer_summary/handler.js" }, { "name": "get_open_items", "statusMessage": "Retrieving your open invoices…", "schema": "./tools/get_open_items/schema.json", "handler": "./tools/get_open_items/handler.js" } ]
FieldRequiredDescription
name✅Tool name — must match function.name in the tool's schema.json. Used by the LLM when it calls the tool.
statusMessage✅Short in-progress message shown in the chat widget while the tool is running (e.g. "Retrieving your open invoices…"). Keep it under ~60 characters.
schema✅Path to the tool's schema.json, relative to the agent-server root.
handler✅Path to the tool's handler.js, relative to the agent-server root.
The MCP server reads tool-registry.json once at startup. After adding or removing tools, restart the agent-server for the changes to take effect.

Adding a tool

Follow these four steps. No server core files need to be modified.

1Create the tool directory

mkdir _DEMO/agent-server/tools/my_new_tool

2Write the schema (schema.json)

Define the tool for the LLM using the OpenAI tool definition format:

{ "type": "function", "function": { "name": "my_new_tool", "description": "What this tool does — write this clearly so the LLM knows when to call it.", "parameters": { "type": "object", "properties": { "exampleParam": { "type": "string", "description": "What this parameter means." } }, "required": ["exampleParam"] } } }

3Write the handler (handler.js)

Export a named execute async function that receives the LLM-supplied arguments and the caller's account context:

export async function execute(args, context) { // args — object matching the parameters declared in schema.json // context — { CompCode, CustNum } from the portal's init() call const { exampleParam } = args; const { CompCode, CustNum } = context; // Call your backend API here — replace with real implementation const data = await fetchFromYourApi(CompCode, CustNum, exampleParam); return data; // return value is serialised to JSON and sent to the LLM }

4Register the tool in tool-registry.json

Add one entry to tools/tool-registry.json:

{ "name": "my_new_tool", "statusMessage": "Fetching your data…", "schema": "./tools/my_new_tool/schema.json", "handler": "./tools/my_new_tool/handler.js" }

Then update lib/system-prompt.txt to describe the new tool in the ## Tools available section so the LLM knows when to call it. Restart the server.

The execute function can call other handlers directly — no need to go through the MCP layer. The existing get_customer_summary handler delegates to get_open_items and get_customer_details this way to avoid duplicating fixture data.

Tool schema reference (schema.json)

Each tool's schema.json is an OpenAI function definition. It controls what the LLM sees — the name, description, and parameter types that the model uses to decide when and how to call the tool.

FieldRequiredDescription
type✅Always "function".
function.name✅Tool identifier — must match the name in tool-registry.json. Use snake_case.
function.description✅Natural-language description of what the tool does and when to use it. This is the most important field for tool-selection quality.
function.parameters✅JSON Schema object describing the tool's input parameters. Use type, properties, description, enum, and required as needed.

Supported parameter types

"parameters": { "type": "object", "properties": { "status": { "type": "string", "enum": ["open", "paid", "pending"], "description": "Filter by payment status." }, "fromDate": { "type": "string", "description": "ISO date (YYYY-MM-DD) — earliest document date filter." }, "$top": { "type": "integer", "description": "Max records to return." }, "includeDetails": { "type": "boolean", "description": "When true, returns full line-item breakdown." } }, "required": ["status"] }
Every parameter description is sent to the LLM in the tools/list response. Write descriptions as instructions to the model — e.g. "Use 'D' to get both invoices and credit memos (default)" rather than just "document type".
Do not declare a _context parameter in your schema. The MCP layer reserves this name to thread account context from the client to the handler. Declaring it would expose it as an LLM-settable argument.

Tool handler reference (handler.js)

Every handler is a plain ES module that exports one named async function: execute.

/** * @param {object} args - LLM-supplied arguments matching schema.json parameters * @param {object} context - Account context from the portal: { CompCode, CustNum } * @returns {*} - Any JSON-serialisable value; sent back to the LLM as a tool result */ export async function execute(args, context) { // implementation }

The context object

The second argument, context, is the exact object the portal passed in init({ context: { … } }). It is never generated by the LLM — it comes from the authenticated session and is injected by the MCP layer.

FieldTypeDescription
context.CompCodestringSAP company code (e.g. "1000"). Identifies which company the account belongs to.
context.CustNumstringZero-padded customer number (e.g. "0000123456"). Identifies the individual account.

Return value

Return any JSON-serialisable value — object, array, or primitive. The MCP layer wraps it in JSON.stringify() and sends it back to the LLM as the tool result. The LLM uses the result to construct the final answer.

// ✅ Good — structured data the LLM can reason about return { balance: 584.00, currency: 'USD', overdue: true }; // ✅ Also fine — an array of records return { d: { results: [ { InvoiceNum: 'INV-2025-0112', … } ] } }; // ❌ Avoid — plain strings lose structure return 'The balance is $584.00';

Error handling

If execute throws, the MCP layer catches the error and returns a structured error result to the LLM:

{ "error": "Tool get_open_items failed — please try again." }

You don't need to catch errors yourself unless you want to return a more specific error message or log additional context.

Server port

The server listens on port 3000 by default. Override with the PORT environment variable in .env:

PORT=8090

If you change the port, update the widget's ai_endpoint and the bundle URL in your portal accordingly.

Request body contract

The agent-server exposes a single endpoint for the widget: POST /ask-assistant. This is what the widget sends on every message.

Request

POST /ask-assistant Authorization: Bearer <bearer_token> Content-Type: application/json { "message": "What is my current balance?", "history": [ { "role": "user", "content": "previous message" }, { "role": "assistant", "content": "previous reply" } ], "context": { "CompCode": "1000", "CustNum": "0000123456" } }
FieldRequiredDescription
message✅The user's current message. Non-empty string.
historyArray of prior conversation turns in { role, content } format. Defaults to []. Capped by the widget's max_turns setting.
contextAccount context object — passed through to every tool handler. Defaults to {} if omitted. Must include CompCode and CustNum for tools to return data.

Response (SSE stream)

The server responds with a Server-Sent Events stream. Three event types are emitted:

HTTP 200 OK Content-Type: text/event-stream # During tool execution (one per tool call): data: {"status": "Retrieving your open invoices…"} # Final answer — one chunk per SSE event, accumulated by the widget: data: {"message": "Your current balance is **$584.00**."} data: {"message": " You have 3 open invoices."} # End of stream: data: [DONE]

The widget renders status events as an in-progress indicator in the chat panel and assembles message chunks into the final answer as they arrive.

Log format

All agent-server log lines follow the pattern:

YYYY-MM-DD HH:MM:SS [label] message

A typical request flow looks like this:

2026-05-16 20:31:14 [request] message="What is my balance?" history=0 turns context={"CompCode":"1000","CustNum":"0000123456"} 2026-05-16 20:31:15 [ai-core] turn-1 812ms finish=tool_calls tokens=312 (prompt=298 + completion=14) 2026-05-16 20:31:15 [agent] tool_calls: get_customer_summary 2026-05-16 20:31:15 [mcp] → get_customer_summary "Pulling together your account summary…" args={} 2026-05-16 20:31:15 [mcp] ← get_customer_summary 4ms result={"d":{"results":[… 2026-05-16 20:31:15 [ai-core] turn-2 streaming... 2026-05-16 20:31:17 [ai-core] turn-2 1923ms chars=387 2026-05-16 20:31:17 [done] total=2741ms
LabelWhen emitted
[server]Server startup — ports and routes
[request]Each incoming POST /ask-assistant
[ai-core]Each LLM API call — duration, finish reason, token counts
[agent]Whether the LLM chose to call tools or answer directly
[mcp]Each tool call — name, status message, args, duration, result preview
[done]End of request — total wall-clock duration
[error]Unhandled exceptions
[mcp-server]Internal MCP subprocess events (written to stderr)

In demo / test mode (./deploy/go.sh --env test), logs are written to _DEMO/agent-server.log and tailed live in the terminal.
