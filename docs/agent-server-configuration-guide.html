Configuration overview

The agent-server has three configurable layers. Each one has a clear owner and is independent of the others — you can change the system prompt without touching the tools, and add a tool without restarting more than the server.

_DEMO/agent-server/
├── .env ← Credentials & server settings (startup config)
├── lib/system-prompt.txt ← LLM persona, tone, and tool guidance (startup config)
└── tools/
    ├── tool-registry.json ← Declares which tools exist
    ├── get_customer_summary/
    │   ├── schema.json ← LLM tool definition (what the model sees)
    │   └── handler.js ← Business logic (what runs when the tool is called)
    ├── get_open_items/ …
    └── …

Startup configuration

Startup configuration

These files are read once when the server starts. Restart the server after any change here.

Environment variables (.env)

Create _DEMO/agent-server/.env from the template below. Variables marked required must be present or the server will fail to start.

# ── SAP AI Core credentials ──────────────────────────────────────────── AICORE_AUTH_URL=https://<subaccount>.authentication.<region>.hana.ondemand.com AICORE_BASE_URL=https://api.ai.prod.<region>.aws.ml.hana.ondemand.com AICORE_CLIENT_ID=sb-<client-id>!b<num>|aicore!b<num> AICORE_CLIENT_SECRET=<client-secret> # ── LLM deployment ───────────────────────────────────────────────────── AICORE_LLM_DEPLOYMENT_ID=<deployment-id> AICORE_LLM_MODEL=gpt-4o # optional — defaults to gpt-4o # ── AI Core settings (optional — safe to omit) ───────────────────────── AICORE_RESOURCE_GROUP=default # defaults to "default" AICORE_API_VERSION=2024-02-01 # defaults to 2024-02-01 # ── Server ───────────────────────────────────────────────────────────── PORT=3000 # optional — defaults to 3000
VariableRequiredDescription
AICORE_AUTH_URL✅ OAuth2 token endpoint base URL for your SAP BTP subaccount. The server appends /oauth/token.
AICORE_BASE_URL✅ SAP AI Core inference API base URL.
AICORE_CLIENT_ID✅ OAuth2 client ID from your AI Core service binding.
AICORE_CLIENT_SECRET✅ OAuth2 client secret from your AI Core service binding.
AICORE_LLM_DEPLOYMENT_ID✅ Deployment ID of the LLM you want to use. Find this in the AI Core console under Deployments.
AICORE_LLM_MODEL Model name sent in the request body. Default: gpt-4o. Must match what the deployment ID targets.
AICORE_RESOURCE_GROUP AI Core resource group. Default: default. Sent as the AI-Resource-Group request header.
AICORE_API_VERSION AI Core API version query parameter. Default: 2024-02-01.
PORT Port the HTTP server listens on. Default: 3000. If you change this, update ai_endpoint and the bundle URL in your portal.
Security: Never commit .env to version control — it contains OAuth2 credentials. The .gitignore already excludes it.
Variables no longer used: EPP_COMP_CODE and EPP_CUST_NUM were removed in v2026.05.16.2031. Account context is now supplied by the caller in the request body. Remove them from your .env if present.

System prompt

The file lib/system-prompt.txt defines the LLM's persona, tone, scope, and tool guidance. It is prepended to every conversation as the system message. This is the primary lever for changing how the assistant behaves — no code changes needed.

Edit this file to:

  • Change the assistant's name, persona, or tone
  • Define what the assistant can and cannot do (scope boundaries)
  • Set response format expectations — e.g. "use markdown", "keep replies under 4 paragraphs"
  • Describe tools so the LLM knows when to call them (see the ## Tools available section)
You are a billing collections agent for Cardinal Rx, an online specialty pharmacy. Your role is to help patients understand and resolve their outstanding balances through clear, empathetic, and professional communication. ## Tone Be empathetic, calm, and solution-focused — medical bills are stressful. Use markdown. Keep responses concise, always ending with a clear next step. ## Tools available - **get_customer_summary** — Best first call for "what do I owe?" questions. Returns open invoices and account info in one request. - **get_open_items** — Detailed list of open invoices and/or credit memos. Use Scenario "D" for a full balance view. …
Always include a ## Tools available section with a description of each registered tool and when to use it. The LLM reads these descriptions to decide which tool to call — a precise description reduces unnecessary calls and improves answer quality.

Server port

Controlled by the PORT environment variable in .env. Defaults to 3000. The server exposes two routes on this port:

RoutePurpose
GET /headless-assistant.jsServes the widget bundle to your portal page
POST /ask-assistantChat API — receives messages, runs the agent, streams the response
Tools

Tools

Tools are what the agent calls to retrieve real account data. Each tool lives in its own directory — a JSON schema that the LLM sees, and a JavaScript handler that runs when the tool is called. Adding a tool requires zero changes to any server file.

Tool registry (tool-registry.json)

tools/tool-registry.json is the single file that declares every tool the agent can use. It maps each tool name to its schema and handler paths.

[ { "name": "get_customer_summary", "statusMessage": "Pulling together your account summary…", "schema": "./tools/get_customer_summary/schema.json", "handler": "./tools/get_customer_summary/handler.js" }, { "name": "get_open_items", "statusMessage": "Retrieving your open invoices…", "schema": "./tools/get_open_items/schema.json", "handler": "./tools/get_open_items/handler.js" } ]
FieldRequiredDescription
name✅Tool identifier — must match function.name in the tool's schema.json. Use snake_case.
statusMessage✅Short in-progress message shown in the chat widget while this tool is running. Keep it under ~60 characters.
schema✅Path to schema.json, relative to the agent-server root.
handler✅Path to handler.js, relative to the agent-server root.
tool-registry.json is read once at startup. After adding, removing, or renaming a tool, restart the agent-server.

Adding a tool — step by step

Four steps. No changes to server.js, agent.js, assistant.js, or any other server file.

1

Create a directory for the tool

mkdir _DEMO/agent-server/tools/my_new_tool
2

Write schema.json — what the LLM sees

This file defines the tool for the model: its name, a description of when to call it, and the parameters it accepts. Write description values as instructions to the LLM — the model reads them to decide whether and how to call the tool.

// tools/my_new_tool/schema.json { "type": "function", "function": { "name": "my_new_tool", "description": "Retrieves X for the current account. Call this when the user asks about Y.", "parameters": { "type": "object", "properties": { "status": { "type": "string", "enum": ["active", "closed"], "description": "Filter by account status. Use 'active' by default." }, "fromDate": { "type": "string", "description": "ISO date (YYYY-MM-DD) — earliest date to include." }, "$top": { "type": "integer", "description": "Max records to return." } }, "required": [] } } }

Schema field reference

FieldRequiredNotes
type✅Always "function".
function.name✅Must match name in tool-registry.json. Use snake_case.
function.description✅The most important field for tool-selection quality. Write it as a model instruction, not just a label.
function.parameters✅Standard JSON Schema object. Supported types: string, integer, boolean, array. Use enum to constrain string values.
Do not declare a _context parameter. That name is reserved by the MCP layer to inject account context — declaring it would expose it as an LLM-settable argument.
3

Write handler.js — what runs when the tool is called

Export a single named execute async function. It receives the LLM-supplied arguments and the authenticated user's account context.

// tools/my_new_tool/handler.js export async function execute(args, context) { // args — matches the parameters declared in schema.json (LLM-supplied) // context — { CompCode, CustNum } from the portal's HeadlessAssistant.init() call const { status, fromDate, $top } = args; const { CompCode, CustNum } = context; // Call your backend API here const data = await fetchFromYourApi({ CompCode, CustNum, status, fromDate, $top }); // Return any JSON-serialisable value — object or array preferred over plain string return data; }

Handler reference

ArgumentTypeDescription
argsobject LLM-supplied values matching your schema.json parameters. Never includes _context — that is stripped by the MCP layer before execute is called.
context.CompCodestring SAP company code (e.g. "1000"). Comes from the portal's init() call — never from the LLM.
context.CustNumstring Zero-padded customer number (e.g. "0000123456"). Same origin as CompCode.

Return value: any JSON-serialisable value. Structured objects let the LLM reason about the data; plain strings lose structure.

// ✅ Good — structured data the LLM can reason about return { balance: 584.00, currency: 'USD', overdue: true }; // ✅ Also fine — an array of records return { d: { results: [ { InvoiceNum: 'INV-2025-0112', … } ] } }; // ❌ Avoid — plain strings lose structure return 'The balance is $584.00';

Error handling: if execute throws, the MCP layer catches it and returns a graceful error result to the LLM. You only need to catch errors yourself when you want to log extra detail or return a specific message.

4

Register in tool-registry.json and update the system prompt

Add one entry to tools/tool-registry.json:

{ "name": "my_new_tool", "statusMessage": "Fetching your data…", "schema": "./tools/my_new_tool/schema.json", "handler": "./tools/my_new_tool/handler.js" }

Then add a line to the ## Tools available section in lib/system-prompt.txt describing the new tool — the LLM reads this to decide when to call it. Restart the server.

A handler can call another handler directly — no need to go through the MCP layer. get_customer_summary does this: it imports and calls get_open_items and get_customer_details directly to avoid duplicating fixture data.
Runtime reference

Runtime reference

Fixed contracts — these do not change when you add tools or edit the system prompt.

Request body contract

The widget sends a POST to /ask-assistant on every message. This is the full request and response shape.

Request

POST /ask-assistant Authorization: Bearer <bearer_token> Content-Type: application/json { "message": "What is my current balance?", // required — non-empty string "history": [ // optional — defaults to [] { "role": "user", "content": "…" }, { "role": "assistant", "content": "…" } ], "context": { // optional — defaults to {} "CompCode": "1000", "CustNum": "0000123456" } }

Response — SSE stream

The server responds immediately with a text/event-stream. Three event types are emitted during a request:

HTTP 200 OK Content-Type: text/event-stream # One status event per tool the agent calls: data: {"status": "Retrieving your open invoices…"} # Final answer — streamed in chunks, assembled by the widget: data: {"message": "Your current balance is **$584.00**."} data: {"message": " You have 3 open invoices due this month."} # End of stream: data: [DONE]
Event fieldWhen emittedWidget behaviour
statusOnce per tool call, before the tool result is receivedDisplays as an in-progress indicator in the chat panel
messageFinal answer, streamed as chunksAccumulated and rendered as markdown
[DONE]End of streamInput is re-enabled; response saved to history

Log format

All log lines follow the pattern YYYY-MM-DD HH:MM:SS [label] message. A complete request — one that triggers a tool call — produces a trace like this:

2026-05-16 20:31:14 [request] message="What is my balance?" history=0 turns context={"CompCode":"1000","CustNum":"0000123456"} 2026-05-16 20:31:15 [ai-core] turn-1 812ms finish=tool_calls tokens=312 (prompt=298 + completion=14) 2026-05-16 20:31:15 [agent] tool_calls: get_customer_summary 2026-05-16 20:31:15 [mcp] → get_customer_summary "Pulling together your account summary…" args={} 2026-05-16 20:31:15 [mcp] ← get_customer_summary 4ms result={"d":{"results":[… 2026-05-16 20:31:15 [ai-core] turn-2 streaming... 2026-05-16 20:31:17 [ai-core] turn-2 1923ms chars=387 2026-05-16 20:31:17 [done] total=2741ms
LabelWhen emitted
[server]Server startup — listening port and routes
[request]Each incoming POST /ask-assistant — message, history length, context
[ai-core]Each LLM API call — duration, finish reason, token counts
[agent]LLM decision — tool calls chosen or direct answer
[mcp]Each tool call — name, status message, args, duration, result preview
[done]End of request — total wall-clock duration
[error]Unhandled exceptions
[mcp-server]Internal MCP subprocess events (written to stderr)

In test mode (./deploy/go.sh --env test), logs are written to _DEMO/agent-server.log and tailed live in the terminal.
