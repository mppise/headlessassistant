Error Handling

How HeadlessAssistant handles API errors, network failures, stream interruptions, and misconfiguration.

Overview

HeadlessAssistant uses a fail-fast, user-initiated recovery model:

  • Errors are never written to conversation history — a failed message attempt leaves the chat clean.
  • Every recoverable error shows a toast notification with a Try again button.
  • There are no automatic retries — the user decides when to retry.

API errors (4xx / 5xx) C01-F17

When your API returns a non-200 HTTP status code (e.g., 429 Too Many Requests, 500 Internal Server Error):

  1. The response body is not read or displayed to the end user.
  2. A toast notification appears above the input: "Something went wrong. Please try again."
  3. A Try again button re-sends the last message.
  4. The toast auto-dismisses after 8 seconds if the user takes no action.
If your API returns detailed error messages in the response body (e.g., { "error": "Rate limit exceeded" }), those are not shown to the end user. Only a generic friendly message is displayed. This is by design — avoid exposing internal API details.

Network / timeout errors C01-F18

When the request cannot reach your server (DNS failure, connection refused, timeout, etc.):

  1. A toast appears: "Could not reach the server. Please check your connection."
  2. A Try again button re-sends the message when clicked.

Stream interruptions C01-F19

When an SSE stream connection drops mid-response:

  1. Whatever text was received before the interruption is preserved and displayed in the chat panel.
  2. A ⚠ Response interrupted indicator is appended to the partial response.
  3. A toast with Try again is shown.
  4. The interrupted partial response is not saved to history — retrying sends a clean request.
When the user clicks Try again after a stream interruption, the widget re-sends the original message with the current conversation history (excluding the interrupted response). Your API receives a clean, fresh request.

API contract

HeadlessAssistant sends the following request to your ai_endpoint on every message:

Request

POST {ai_endpoint} Authorization: Bearer {bearer_token} Content-Type: application/json { "customer_id": "CUST-00123-or-anonymous-uuid", "message": "the user's message text", "history": [ { "role": "user", "content": "previous user message" }, { "role": "assistant", "content": "previous assistant reply" } ] }

customer_id is the value supplied via the customer_id config field, or an auto-generated anonymous UUID when that field is omitted. See User identity for details.

Full JSON response (stream_mode: "json")

HTTP 200 OK Content-Type: application/json { "message": "## Hello\n\nThis is the **assistant** response in markdown." }

The field name ("message") is configurable via response_field in your config. Dot-notation is supported (e.g., "data.reply").

SSE streaming response (stream_mode: "sse")

HTTP 200 OK Content-Type: text/event-stream data: {"message": "## Hello\n\n"} data: {"message": "This is the **assistant**"} data: {"message": " response in markdown."} data: [DONE]

Each SSE event delivers a chunk of the markdown response. HeadlessAssistant accumulates chunks and re-renders the full markdown on each one. The stream ends on a [DONE] sentinel or server-side connection close.

Config errors

If required config fields (ai_endpoint, bearer_token) are missing, or if the JSON config file cannot be fetched, the widget renders a visible error message and halts:

  • "Assistant configuration is incomplete. Contact the site administrator." — missing required fields.
  • "Could not load assistant configuration." — config JSON file not found or unreachable.

Check the browser console for additional diagnostic detail.
