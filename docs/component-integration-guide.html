Prerequisites

Before embedding the widget you need:

  • A running agent-server instance. It serves both the widget bundle (GET /headless-assistant.js) and the chat API (POST /ask-assistant). See the Agent Server Configuration Guide for setup.
  • A short-lived Bearer token for the /ask-assistant endpoint, generated server-side.
  • The authenticated user's account identifiers — CompCode and CustNum — available at page load time so the agent can look up their data.

No build tool, package manager, or framework is required on the portal page.

Choose an integration method

HeadlessAssistant supports two ways to configure and mount the widget. Pick the one that fits your portal.

Method 1 — Manual init Recommended
JavaScript · runtime values · authenticated portals
  • Call HeadlessAssistant.init(config) from JavaScript
  • Config is a plain JS object — inject any runtime value (user session, tokens)
  • CompCode / CustNum come from the authenticated session, not a static file
  • Works in frameworks (React, Angular, Vue) and vanilla JS
Method 2 — Auto-init
Script tag · JSON file · static pages
  • Add a <script> tag with a data-config attribute
  • Widget mounts automatically — no JavaScript required
  • Config comes from a JSON file fetched at runtime
  • Best for static pages where account identifiers are fixed or not needed
Not sure which to use? If the portal has an authenticated user session (which is the common case for a billing assistant), use Method 1. It lets you read CompCode and CustNum from the session and pass them at init time — no static file needed.

Method 1 — Manual init Recommended

Configure and mount the widget with a JavaScript object. Account identifiers and tokens are injected at runtime from your server-side session.

1

Load the widget bundle

Add a <script> tag in your page's <head> or at the end of <body>. The bundle is served directly by the agent-server.

<script src="https://your-agent-server/headless-assistant.js"></script>
2

Call HeadlessAssistant.init()

Call init() after the script loads, passing a config object. Read CompCode, CustNum, and the bearer token from your server-rendered page or session API — never hardcode them.

<script> HeadlessAssistant.init({ // ── Required ─────────────────────────────────────────────────────── ai_endpoint: 'https://your-agent-server/ask-assistant', bearer_token: 'short-lived-scoped-token-from-your-server', // ── Account context (required for tools to return data) ──────────── context: { CompCode: '1000', // from authenticated session CustNum: '0000123456' // from authenticated session }, // ── Optional ─────────────────────────────────────────────────────── user_name: 'Sarah Johnson', // first name shown in greeting bubble max_turns: 10, stream_mode: 'sse', theme: { header_title: 'Billing Assistant', placeholder_text: 'Ask about invoices, payments, or coverage…', primary_color: '#CC0000' } }); </script>
If user_name is supplied and there is no prior conversation history, the widget greets the user by first name when the panel opens — e.g. "Hi Sarah! How can I help you today?" The greeting is not saved to history.
Calling init() while the widget is already mounted is a no-op. Call HeadlessAssistant.destroy() first if you need to re-mount with a different config.

Method 2 — Auto-init via script tag

The widget reads its config from a JSON file and mounts itself automatically — no JavaScript required on your page.

1

Create a config file

Save this JSON file somewhere your page can fetch it (same server, CDN, etc.).

// headless-assistant.config.json { "ai_endpoint": "https://your-agent-server/ask-assistant", "bearer_token": "your-short-lived-scoped-token", "context": { "CompCode": "1000", "CustNum": "0000123456" }, "max_turns": 10, "stream_mode": "sse", "theme": { "header_title": "Billing Assistant", "placeholder_text": "Ask about invoices or payments…", "primary_color": "#4F46E5" } }
2

Add the script tag with data-config

Point the data-config attribute at the JSON file. The widget fetches it and mounts automatically — no further JavaScript needed.

<script src="https://your-agent-server/headless-assistant.js" data-config="/path/to/headless-assistant.config.json"> </script>
Limitation: the config file is static. CompCode and CustNum are fixed at file-write time and cannot be injected from an authenticated session. Use Method 1 whenever account context must come from a live user session.

Widget display modes

Both integration methods support two display modes. Choose based on where you want the widget to appear on the page.

Floating bubble
Default — no container needed
  • Widget renders as a fixed chat bubble in the bottom-right corner
  • Clicking the bubble opens the chat panel
  • ✕ in the panel header collapses back to bubble
  • No HTML changes needed — widget injects its own DOM
Inline embed
Pass a container selector
  • Widget fills a container element you specify
  • Visible immediately — no bubble, no toggle
  • Use for a dedicated support tab or sidebar panel
  • Container must exist in the DOM before init() is called

Floating bubble — no extra HTML needed

Omit the container field and the widget automatically places itself in the corner:

HeadlessAssistant.init({ ai_endpoint: 'https://your-agent-server/ask-assistant', bearer_token: 'your-token', context: { CompCode: '1000', CustNum: '0000123456' } // no container → floating bubble });

Inline embed — specify a container

Add an element to your HTML, then pass its CSS selector as container:

<!-- Add a container element in your HTML --> <div id="billing-assistant" style="width: 420px; height: 520px;"></div>
HeadlessAssistant.init({ ai_endpoint: 'https://your-agent-server/ask-assistant', bearer_token: 'your-token', context: { CompCode: '1000', CustNum: '0000123456' }, container: '#billing-assistant' // ← CSS selector });
The container element must exist in the DOM at the time init() is called. If the selector matches nothing, the widget renders an error and halts.

Config reference

All fields work identically whether you supply them as a JS object (Method 1) or in a JSON config file (Method 2).

FieldTypeRequiredDefaultDescription
ai_endpointstring✅— Full URL of the agent-server's /ask-assistant endpoint
bearer_tokenstring✅— Sent as Authorization: Bearer … on every request. Use a short-lived, scoped token.
contextobject{} Account identifiers forwarded verbatim to the agent-server. Must include CompCode and CustNum for tools to return data. See Passing account context.
user_namestring— Display name shown in the greeting bubble on a fresh session. Only the first token is used — e.g. "Sarah M. Johnson" → "Hi Sarah!". Omit to skip the greeting.
customer_idstringauto UUID Sent as customer_id in every request body. If omitted, the widget generates a crypto.randomUUID() and persists it in localStorage under ha_user_id.
containerstring— CSS selector for inline embed target. Omit for floating bubble mode.
max_turnsnumber10 Maximum number of prior conversation turns sent to the API per request (1–100).
stream_mode"sse" | "json""sse" Response format — SSE streaming or a single JSON response. The agent-server uses "sse".
response_fieldstring"message" Dot-notation path to the markdown content in a full JSON response (e.g. "data.reply").
stream_fieldstringsame as response_field Dot-notation path to the markdown chunk in each SSE event.
theme.*objectsee theming guide Visual customisation — colors, fonts, header text. See the Theming guide.

Passing account context

The context object carries the authenticated user's account identifiers to every tool the agent calls. Without it the agent cannot look up balances, invoices, or account details — tools will return empty results.

The widget forwards context verbatim in every POST request body:

// What the widget sends to /ask-assistant on every message: { "message": "What is my current balance?", "history": [...], "context": { "CompCode": "1000", "CustNum": "0000123456" } }
FieldDescription
context.CompCodeSAP company code (e.g. "1000"). Identifies which company the account belongs to.
context.CustNumZero-padded customer number (e.g. "0000123456"). Identifies the individual account.
If context is omitted, the agent-server defaults to {} and all tool calls will return incomplete results.
Read CompCode and CustNum from your server-side session and inject them at init() time. Never hardcode them in a static file checked into source control.

Clear history

Conversation history is stored in localStorage. It can be cleared two ways:

  • Via the widget UI: the trash icon in the widget header wipes all stored turns immediately.
  • Programmatically: call HeadlessAssistant.clearHistory() from your page at any time — for example, on logout.
document.querySelector('#logout-btn').addEventListener('click', () => { HeadlessAssistant.clearHistory(); logoutUser(); });
Clearing history also resets the anonymous UUID in localStorage. If you supply customer_id in config, that value is unaffected — only the auto-generated UUID is reset.

Destroy (SPA teardown)

In Single Page Applications, call HeadlessAssistant.destroy() when the route containing the widget is unmounted. This removes all widget DOM nodes and event listeners.

// React — cleanup in useEffect useEffect(() => { HeadlessAssistant.init({ ai_endpoint: 'https://your-agent-server/ask-assistant', bearer_token: 'your-token', context: { CompCode: '1000', CustNum: '0000123456' } }); return () => HeadlessAssistant.destroy(); }, []);
destroy() does not clear localStorage. Conversation history is preserved until the user clears it or you call clearHistory().

Config errors

If required fields are missing or invalid, the widget renders a visible error message and halts — it does not throw uncaught JavaScript exceptions. Common causes:

  • ai_endpoint is missing or empty.
  • bearer_token is missing or empty.
  • The data-config URL returns a 404 or network error (auto-init only).
  • The container selector matches nothing in the DOM.

Check the browser console for details. The error is displayed where the widget would have appeared.

Security notes

Your bearer token is visible in the browser. Anyone who can view your page source or network traffic can read it. Always use a short-lived, scoped token generated server-side — never an API master key.
  • Rotate tokens regularly and expire them quickly (minutes to hours, not days).
  • Scope the token so it can only reach your chat endpoint — not admin or write endpoints.
  • HeadlessAssistant sanitizes all API response content before rendering to prevent XSS.
  • Conversation history in localStorage is readable by any JavaScript on the same domain. Do not send sensitive data through the widget if your portal runs untrusted third-party scripts.
  • The context object is sent in the request body — supply it from a server-side session, not hardcoded in client JavaScript.
